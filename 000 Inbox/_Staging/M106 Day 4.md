# Funktionen

## Vordefinierte SQL-Funktionen <a href="#vordefinierte-sql-funktionen" id="vordefinierte-sql-funktionen"></a>

SQL Server stellt eine riesige Menge vordefinierter (integrierter) Funktionen zur Verfügung. Eine integrierte SQL Server-Funktion ist entweder deterministisch oder nicht deterministisch.

* Funktionen sind *deterministisch*, wenn sie bei jedem Aufrufen mit bestimmten Eingabewerten immer das gleiche Ergebnis zurückgeben.
* Funktionen sind *nicht deterministisch*, wenn sie bei jedem Aufrufen selbst mit denselben bestimmten Eingabewerten verschiedene Ergebnisse zurückliefern können.

{% hint style="warning" %}
WICHTIG: Vordefinierte Funktionen wirken sich bei deren Ausführung nur auf die Anzeige aus, nicht jedoch auf die in der Datenbank gespeicherten Daten. Diese werden in keiner Weise verändert!
{% endhint %}

Bei den hier behandelten Funktionen handelt es sich um sogenannte **Single-Row-Funktionen** (Skalar-Funktionen). Diese liefern aus einem Ausdruck einer Zeile einen Wert zurück. Im Gegensatz dazu fassen Multiple-Row-Funktionen (auch als Aggregatfunktionen bekannt) mehrere Werte aus unterschiedlichen Datensätzen zu einem Wert zusammen. Single-Row- bzw. Skalar-Funktionen werden für jede Zeile einmal separat ausgeführt und können sowohl in der `SELECT`- als auch in der `WHERE`-Klausel verwendet werden.\
Single-Row-Funktionen können keine, eine oder mehrere Übergabeparameter (auch Argumente genannt) besitzen. Auch hier gibt es Syntax-Unterschiede bei den Herstellern. Der gesamte Funktionsumfang ist jedoch sehr ähnlich. Funktionen lassen sich in verschiedene Typen einteilen. Oft verwendete Typen sind:

* Zeichenfolgenfunktionen
* Mathematische Funktionen
* Datums- und Uhrzeitfunktionen
* Konvertierungsfunktionen
* Systemfunktionen

# Ausführungsplan

## Diagnose von Datenbankabfragen

Um mögliche Flaschenhälse bei einer Datenbankabfrage ausfindig zu machen, kann ein **Ausführungsplan (Explain Plan)** generiert werden. Ein Ausführungsplan zeigt auf, wo bei einer Abfrage die meisten Ressourcen verbraucht werden und liefert so eine gute Grundlage, um die Performance von Abfragen optimieren zu können.

Viele DBMS bieten dazu einen speziellen `EXPLAIN`-Befehl an, welcher einfach beispielsweise vor dem SELECT-Statement abgesetzt wird:

```sql
EXPLAIN SELECT * from tbl_name;
```

Bei SQL Server gibt es diesen Befehl nicht, dafür andere Möglichkeiten.

### Möglichkeit 1

Im Azure Data-Studio kannst du die `Estimated Plan`-Funktion mit einem Klick auf den folgenden Button aufrufen.

# Indizes

Oft werden bei Anfragen nur einige wenige Tupel benötigt. Sind die Datensätze ohne Zusatz-informationen in einer Datei gespeichert, muss die ganze Datei durchsucht werden, um die angefragten Tupel zu finden. Sinnvoller wären Direktzugriffsmöglichkeiten.

## Erstellen eines Index

Je nach Ergebnis des Ausführungsplans ist es ratsam, **Indizes** zu erstellen. Indizes hängen an einer Tabelle oder einer View und sind probate Mittel, um Abfragen zu beschleunigen.&#x20;

In SQL Server gibt es verschiedene Typen von Indizes. In diesem Kurs konzentrieren wir uns auf c*lustered* und *nonclustered* Indizes. Diese beiden Typen sind sogenannte *Rowstore* Indizes und kommen vor allem dann zur Anwendung, wenn bei einer Abfrage spezifische Spalten ausgewählt oder sortiert und möglichst schnell ausgegeben werden sollen.

### Nonclustered Index

```sql
-- Nonclustered Index auf einer Tabelle erstellen 
CREATE INDEX index_name ON schema_name.table_name (column_name);
```

Ohne Angabe des Schlüsselwortes `CLUSTERED` wird defaultmässig ein *nonclustered* Index erstellt. Ein *nonclustered* Index spezifiziert nur die logische Sortierung einer Tabelle, nicht aber die physische. Die gespeicherten Datensätze der Tabelle sind also nicht sortiert.&#x20;

Vereinfacht gesagt ist ein *nonclustered* Index nur ein **Zeiger (Verweis)** auf den Datensatz, vergleichbar mit einem Stichwortverzeichnis am Ende eines Buches: Ist das Stichwort gefunden, steht dahinter lediglich die Seitenzahl, wo der entsprechende Eintrag zu finden ist. Wird bei einer Datenbankabfrage eine indizierte Spalte als Suchkriterium herangezogen, sucht das DBMS die gewünschten Datensätze anhand dieser Verweise.&#x20;

Die folgende Abbildung zeigt das Prinzip. Jeder Index-Eintrag (Blattknoten) besteht aus einer Kopie der in­di­zie­rten Spalte (`Spalte 2`) und einem Verweis (`ROWID` ) auf den entsprechenden physischen Speicherort des Eintrags in der Tabelle.

<div align="left"><img src="/files/uNWzAxf0Myzvija6Mihd" alt="Bild: https://use-the-index-luke.com/de/sql/anatomie/index-blaetter "></div>

Ein grosser Vorteil eines *nonclustered* Index ist, dass es in einer Tabelle mehrere davon geben kann, die nach unterschiedlichen Spalten sortiert sind. Bedenke aber, dass es nicht sinnvoll ist, für jede einzelne Spalte einen separaten Index zu erzeugen, da Indices gewartet werden müssen: bei jeder Änderung von Daten (`INSERT`, `UPDATE`) müssen auch die von den Änderungen betroffenen Indizes aktualisiert werden, damit diese weiterhin ihre Wirkung erzielen.&#x20;

{% hint style="warning" %}
Als Grundregel kann man sich merken, dass zusätzliche Indizes die Lesezugriffe zwar beschleunigen können, die Schreibzugriffe aber verlangsamen.
{% endhint %}

### Clustered Index

Jede Tabelle sollte bekanntlich über einen Primärschlüssel verfügen. In der Praxis wird für einen c*lustered* Index meist die Spalte mit dem Primärschlüssel genutzt, da alle Werte in dieser Spalte eindeutig sind. So wird bei der Erstellung eines Primärschlüssels implizit ein *clustered* Index erzeugt, wie folgendes Beispiel zeigt.&#x20;

```sql
-- Explizites Erstellen eines clustered Index auf einer Tabelle
CREATE CLUSTERED INDEX index_name ON schema_name.table_name (column_name);

-- Implizites Erstellen eines clustered Index durch einen Primärschlüssel
ALTER TABLE table_name
ADD CONSTRAINT constraint_name
PRIMARY KEY CLUSTERED (column_name);
```

Bei einem *clustered* Index bestimmt die logische Reihenfolge der Schlüsselwerte die physische Reihenfolge der entsprechenden Zeilen in einer Tabelle. Die aktuellen Zeilen sind dabei in der untersten Ebene des *clustered* Indexes gespeichert.&#x20;

Ein Nachteil von *clustered* Indizes: Wird bei einer Abfrage anhand einer Spalte gesucht, welche keinen *clustered* Index hat, kann von dem Index auf der Primärschlüssel-Spalte nicht profitiert werden. Zudem ist pro Tabelle nur ein *clustered* Index erlaubt.

### Unique Index

*Clustered* sowie *nonclustered Indizes* können beide unique sein. Das heisst, dass die zu einem Index-Schlüssel gehörigen Werte eindeutig sein müssen und nur ein Mal vorkommen dürfen. Auf Spalten, in welchen bereits doppelte Werte vorkommen, können demzufolge keine *unique* Indizes erzeugt werden. Mehrfach vorhandene `NULL`-Werte werden übrigens ebenfalls als Duplikate erkannt.

```sql
-- Unique Index auf einer Spalte erstellen
CREATE UNIQUE INDEX index_name ON table_name (column_name);
```

## Kriterien für die Erstellung von Indizes

Die Entscheidung, ob und für welche Spalten ein Index sinnvoll ist, lässt sich anhand folgender Kriterien treffen:

* Die Tabelle verfügt über eine grosse Anzahl von Datensätzen.
* Wird in Abfragen oft nach der Spalte gesucht oder gefiltert, spricht dies für einen Index.
* Dasselbe gilt für Spalten, die als Fremdschlüsselspalten verwendet werden, da auf diese bei einem JOIN gefiltert wird.
* Beinhaltet die Spalte nur wenige verschiedene Werte (man redet dann auch von geringer Selektivität), spricht dies eher gegen einen Index darauf. Dies gilt insbesondere für Spalten, die den Datentyp *Bit* verwenden.
* Wird die Tabelle meist gelesen und nur selten geändert, sind mehr Indizes vertretbar.
* Wird einer Tabelle primär geschrieben (z. B. eine Protokolltabelle) und nur selten gelesen, sollte man die Anzahl der Indizes möglichst gering halten.

# Datenbanksicherung

## Zweck von Sicherungen

Um Datenverluste infolge von Benutzer- oder Hardwarefehlern, Naturkatastrophen oder Cyberattacken zu vermeiden, müssen die Daten regelmässig gesichert werden. Dazu bietet SQL Server einige Mechanismen an.

## Sicherungsvarianten

SQL Server unterstützt die folgenden Sicherungsvarianten.

### **Vollständige Datenbanksicherung**&#x20;

Eine vollständige Datenbanksicherung enthält alle Daten der betreffenden Datenbank zum Zeitpunkt der Sicherung. Bei einem Restore wird aus dieser Sicherung die komplette Datenbank wiederhergestellt.

```sql
BACKUP DATABASE [WideWorldImporters]
TO DISK = N'C:\Program Files\Microsoft SQL Server\MSSQL16.MSSQLSERVER\MSSQL\Backup\WideWorldImporters.bak' 
WITH NOFORMAT, NOINIT, NAME = N'WideWorldImporters vollständige Datenbanksicherung', SKIP, STATS = 10
GO
```

| Option                     | Beschreibung                                                                  |
| -------------------------- | ----------------------------------------------------------------------------- |
| `WITH FORMAT`              | Überschreibt alle vorhandenen Sicherungen und erstellt einen neuen Mediensatz |
| `WITH NOFORMAT` (Standard) | Fügt das Backup zur Datei hinzu                                               |
| `NOINIT` (Standard)        | Belässt den Header eines existierenden Backups                                |
| `SKIP`                     | Zusammen mit `NOINIT`belässt es ein existierendes Backups                     |
| `STATS = N`                | Schreibt eine Nachricht auf die Konsole für jede `N`Prozent Fortschritt       |

### **Differenzielle Sicherung**&#x20;

Die differenzielle Sicherung basiert auf der letzten vollständigen Sicherung und enthält nur die Daten, die sich seitdem geändert haben. Es werden nur jene Datenblöcke gesichert, die sich seit der letzten vollständigen Sicherung geändert haben. Bei einem Restore wird auch die entsprechende Vollsicherung benötigt. Voraussetzung für die differenzielle Sicherung ist also eine vollständige Datenbanksicherung.&#x20;

```sql
BACKUP DATABASE [WideWorldImporters]   
TO DISK = N'C:\Program Files\Microsoft SQL Server\MSSQL16.MSSQLSERVER\MSSQL\Backup\WideWorldImporters_DIFF.bak'   
WITH DIFFERENTIAL;  
GO 
```

### **Transaktionsprotokoll-Sicherung**

Das Transaktionsprotokoll beinhaltet alle Veränderungen auf der Datenbank, die seit der letzten vollständigen, differenziellen oder Transaktionsprotokoll-Sicherung abgeschlossen wurden. Mithilfe einer Transaktionsprotokollsicherung kann der Zustand der Datenbank bei einem Ausfall bis zu diesem Zeitpunkt wiederhergestellt werden.

```sql
/*Nur im Wiederherstellungsmodell "vollständig" möglich und 
wenn bereits eine Datenbanksicherung vorhanden ist*/
BACKUP LOG [WideWorldImporters]
TO DISK = N'C:\Program Files\Microsoft SQL Server\MSSQL16.MSSQLSERVER\MSSQL\Backup\WideWorldImporters_LOG.trn'  
WITH INIT, NAME = N'WideWorldImporters_Log'
GO
```

## Sicherungsziele

Die gängigste Methode ist, Datenbanksicherungen auf einer Festplatte auf einem anderen Server anzulegen. Alternativ kann auch eine abgesicherte Cloud als Speicherort genutzt werden. Aus Sicherheitsgründen sollten Datenbank und Sicherung auf separaten Medien platziert werden.&#x20;

### Sicherungsmedium

Ein Sicherungsmedium ist eine Datei, in welcher ein oder mehrere Sicherungssätze gespeichert werden können. Ein Sicherungssatz ist das Ergebnis einer vollständigen oder differenziellen Sicherung und wird als .bak-Datei abgelegt.&#x20;

Wenn der gleiche Dateiname für mehrere Sicherungen der Datenbank verwendet wird, wird die Backup-Datei mit den Standardeinstellungen nicht überschrieben, sondern der Sicherungsvorgang wird eine weitere, zusätzliche Sicherung in dieser Datei (*Sicherungsmedium*) speichern.

Ein Sicherungsmedium ermöglicht es, einfach auf Sicherungsziele zuzugreifen, ohne sich jedes Mal über Pfade und Speicherorte Gedanken machen zu müssen. Dadurch erhöht sich die Übersicht beim Sichern. Beim Anlegen eines solchen Mediums wird ein Ziel festgelegt, auf das in der Folge über den Namen des Mediums zugegriffen werden kann.&#x20;

### Wiederherstellungsmodelle bei SQL Server

Die Wahl der Sicherungsvariante hängt eng mit dem Wiederherstellungsmodell der Datenbank zusammen. Beim Wiederherstellungsmodell handelt es sich um eine Datenbankeigenschaft, welche festlegt, wie SQL Server die Daten zum Transaktionsprotokoll speichert und verwaltet, wenn die Transaktionen abgeschlossen sind. In SQL stehen drei Modelle zur Auswahl:&#x20;

**Einfach**: SQL Server verwaltet das zugehörige Transaktionsprotokoll automatisch, inaktive Teile des Protokolls werden automatisch gelöscht. Das Transaktionsprotokoll wird automatisch abgeschnitten, sobald die Transaktionen sicher im dauerhaften Speicher angekommen sind. Das Transaktionsprotokoll wird somit immer klein gehalten und kann nicht unbegrenzt wachsen. Nachteil: Das Transaktionsprotokoll kann nicht extra gesichert werden. Dieses Modell wird nur bei Test- oder Entwicklungsdatenbanken empfohlen.&#x20;

**Vollständig** (point-in-time recovery): Es werden alle Transaktionen im Protokoll gehalten und der inaktive Teil nicht gelöscht. Erst wenn die Transaktionsprotokollsicherung ausgeführt wird, wird der inaktive Teil gelöscht. Im Fall einer Wiederherstellung der Datenbank wird zuerst die DB Sicherung und danach die Transaktionsprotokollsicherung eingespielt. Denn nur mit der Transaktionsprotokollsicherung erreicht man, dass alles bis zur letzten Datenbankänderung restored wurde. Nachteil: Das Transaktionsprotokoll kann schnell ziemlich gross werden, falls nicht laufend eine Transaktionsprotokoll- Sicherung durchgeführt wird und dieses gelöscht wird. In diesem Fall läuft man Gefahr, dass die Festplatte voll und die Datenbank lahmgelegt wird. Dieses Modell wird üblicherweise bei Produktionsdatenbanken verwendet.&#x20;

**Massenprotokolliert**: Ähnlich wie beim vollständigen Modell, das Transaktionsprotokoll wächst allerdings nicht so schnell. Diese Option wird vor allem bei Datenbanken mit vielen Massenoperationen (bulk inserts) gewählt.

### Aufgabe 6

Erstelle eine View *lohnuebersicht*, welche den Vornahmen, Nachnahmen und das Gehalt ausgibt. Die Jahresgehälter werden jeden Monat um 30$ erhöht. Da immer wieder eine Lohnliste erstellt werden muss, machst du eine View. Diese View soll also den Grundlohn ausgeben plus eine Spalte mit der kumulierten Lohnerhöhung.&#x20;

Zusatzaufgabe: Mitarbeiter, welche im Jahre 1993 eingestellt wurden, erhalten zudem jährlich noch einen Bonus von 1000$ - die View erhält eine weitere Spalte mit dem kumulierten Bonus.

Tipps zum Vorgehen:&#x20;

* Erstelle zuerst ein funktionierendes SELECT Statement ohne VIEW, welche die gewünschten Daten liefert. Erstelle die View daraus erst, wenn das SELECT-Statemend korrekt funktioniert.
* Zur leichteren Kontrolle kannst du zusätzlich das HireDate und die Anzahl Monate seit Anstellung in eigenen Spalten ausgeben.

### Aufgabe 7

### Aufgabe 8

Die neue Spalte soll von *valutation* in *rating* umbenannt werden.

Tipp: In Aufgabe 7 wird ein Constraint erstellt wird (CHECK), dieser muss zuerst gelöscht werden:&#x20;

1. Den Constraint-Namen zum Löschen findest du in der Tabellen-Beschreibung unter "Constraints" unter dem Namen "CK\_\_Employees\_\_valut\_\_xxxxxxxx", z.B. "CK\_\_Employees\_\_valut\_\_03F0984C".
2. Constraint löschen

   ```sql
   ALTER TABLE Employees DROP CONSTRAINT ...
   ```
3. Spalte umbenennen
4. Dann der Constraint wieder hinzufügen

   ```sql
   ALTER TABLE Employees ADD ...
   ```
